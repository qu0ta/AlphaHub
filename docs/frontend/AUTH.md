# Авторизация и сценарии UI

## Регистрация и вход

1. Соберите name/email/password. Подтверждение пароля проверяйте только на клиенте.
2. Проверьте обязательность и 8–72 UTF-8 байта пароля.
3. Отправьте register только с предусмотренными полями.
4. При 201 аккаунт создан; для автоматического входа отдельно вызовите login.
5. С access_token вызовите me, сохраните токен и профиль, откройте приватные экраны.

Если register успешен, а login завершился ошибкой, аккаунт уже есть.
Предложите повторить вход; не повторяйте регистрацию автоматически.
Для обычного входа достаточно login → me.
После операции не сохраняйте пароль. Пока форма отправляется, блокируйте повторную отправку.

## Восстановление сессии

Рекомендуемые состояния: initializing, anonymous, authenticated, temporary-error.

| Ситуация | Действие |
| --- | --- |
| Токена нет | anonymous |
| Токен есть | initializing, запрос me |
| me = 200 | authenticated, сохранить актуальный профиль |
| me = 401 | Удалить токен/профиль/приватный кэш, anonymous |
| me = 500 или сеть недоступна | temporary-error с повтором; не считать доказанным выходом |

Не показывайте приватные экраны до проверки.
Отменяйте устаревшие запросы или проверяйте актуальность сессии перед записью результата:
поздний ответ me не должен восстановить сессию после выхода.
401 login — ошибка формы входа, а не сигнал глобального обработчика истёкшей сессии.

## JWT

HS256, срок выдачи 2 часа.

| Claim | Тип | Значение при выдаче |
| --- | --- | --- |
| sub | string | ID пользователя |
| iss | string | alphahub-api |
| iat | number | Unix timestamp в секундах |
| exp | number | Unix timestamp в секундах, iat + 7200 |
| role | string | Роль при входе |

Backend проверяет алгоритм, подпись, issuer, обязательный exp, срок,
issued-at при наличии и непустой subject.
Декодирование JWT фронтом не проверяет подлинность. exp можно читать для UI;
для JS Date умножайте на 1000.
Роль токена может устареть; me читает актуальные данные БД.

JWT_SECRET нужен только backend: не помещать в frontend env, bundle или запросы.
Refresh token отсутствует. После истечения нужен повторный login.

## Хранение и выход

API отдаёт токен в JSON, HttpOnly cookie не устанавливает.
Пример интеграции хранит токен в памяти: перезагрузка завершает сессию.
Для постоянной сессии отдельно выберите хранение.
sessionStorage переживает перезагрузку вкладки; localStorage — также перезапуск браузера.
Оба доступны JS и требуют защиты от XSS. Это варианты клиента, не требования API.

Выход на фронте: очистить токен, профиль, приватный кэш; отменить запросы и перейти на вход.
Серверного logout/revoke нет: выданный токен действителен до exp.
Не вызывайте несуществующие /logout или /refresh.

## Роли, компания, ошибки

CLIENT назначается при публичной регистрации.
BANK_EMPLOYEE допустим для существующей записи. API назначения роли/компании нет.
company_id необязателен, отсутствие не ошибка.
Для неизвестной роли рекомендуется контролируемое состояние UI.
Скрытие кнопок по роли не заменяет серверную авторизацию; API банковских действий пока нет.

Сообщения интерфейса сопоставляйте прежде всего по операции и статусу.
409 register: предложить вход. 401 me: завершить локальную сессию.
5xx/сеть: предложить повтор без автоматической повторной регистрации.
Не логируйте пароль/токен, не включайте в URL и аналитику.
Выводите пользовательские строки как текст, не innerHTML.
