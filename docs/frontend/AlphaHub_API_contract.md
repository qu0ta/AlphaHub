# Контракт HTTP API — AlphaHub

## Общие правила

- Базовый адрес локального API: `http://localhost:8080`.
- Для `register` и `login` передавайте `Content-Type: application/json`; рекомендуется `Accept: application/json`.
- Успешные ответы: `application/json`. `register`, `login`, `me` и получение продукта по коду возвращают объекты без
  обёртки. Каталог продуктов возвращает массив без обёртки.
- Ошибки обработчиков: `text/plain; charset=utf-8`, текст с завершающим переводом строки.
- Единого формата JSON-ошибок, `error.code` и request ID пока нет.
- Для JSON-запросов авторизации установлен лимит тела 8192 байта, ожидается один JSON-объект с известными полями.
  Неизвестные поля отклоняются декодером. В текущей реализации `login` ошибка декодирования может игнорироваться — не
  следует полагаться на единообразную обработку некорректного JSON.
- `Content-Type` входящих запросов явно не проверяется.
- Path-параметры используются там, где явно указаны (например, `{code}`). Query-параметры текущими обработчиками не
  используются.
- Маршруты с завершающим `/` отдельно не зарегистрированы. Неизвестный путь — стандартный `404` Go ServeMux; неверный
  метод — `405` с `Allow`.
- В Go ServeMux `GET` также допускает `HEAD`, при этом тело ответа не передаётся.

## UserResponse

| Поле         | Тип    | Наличие       | Значение                                      |
|--------------|--------|---------------|-----------------------------------------------|
| `id`         | string | Всегда        | UUID пользователя                             |
| `name`       | string | Всегда        | Имя                                           |
| `email`      | string | Всегда        | Email                                         |
| `role`       | string | Всегда        | `CLIENT` или `BANK_EMPLOYEE`                  |
| `company_id` | string | Необязательно | UUID компании; пустая строка не сериализуется |

```json
{
  "id": "86e85897-d21d-4a64-a4a0-00e04a479aef",
  "name": "Анна",
  "email": "anna@example.com",
  "role": "CLIENT"
}
```

Пароль и `password_hash` не возвращаются. UUID передаются строками. Публичного API назначения компании или создания
сотрудника банка пока нет.

## POST /api/v1/auth/register

Авторизация не нужна.

```json
{
  "name": "Анна",
  "email": "anna@example.com",
  "password": "ExamplePass123!"
}
```

| Поле       | Тип    | Проверка                                                                                        |
|------------|--------|-------------------------------------------------------------------------------------------------|
| `name`     | string | Обязательно; `TrimSpace`, затем непустое                                                        |
| `email`    | string | Обязательно; `TrimSpace`, lowercase, `mail.ParseAddress` и соответствие нормализованному адресу |
| `password` | string | Обязательно; 8–72 байта UTF-8 включительно                                                      |

- Email передавайте без отображаемого имени вида `Name <email>`.
- Пароль не обрезается и не нормализуется. Требований к цифрам, спецсимволам и регистру нет.
- Длину пароля на фронтенде определяйте через `new TextEncoder().encode(password).length`, а не `string.length`.
- Проверки следуют в порядке: имя → email → пароль.
- `name` и `email` ограничены в БД `VARCHAR(255)`; текущая сервисная валидация может не учитывать эту длину.
- Не передавайте `id`, `role`, `company_id`, `password_hash`, `password_confirmation`.

**Успех:** `201 Created`, объект `UserResponse`. Роль всегда `CLIENT`, `company_id` отсутствует. Токен и cookie не
выдаются.

| HTTP | Текст ошибки                       | Причина                                                              |
|------|------------------------------------|----------------------------------------------------------------------|
| 400  | `Invalid register request`         | Некорректный JSON, неизвестное поле, неверный тип, превышение лимита |
| 400  | `name is required`                 | Пустое имя                                                           |
| 400  | `invalid email`                    | Неверный email                                                       |
| 400  | `password must contain 8-72 bytes` | Неверная длина пароля                                                |
| 409  | `Email already registered`         | Email уже зарегистрирован                                            |
| 500  | `Internal server error`            | Ошибка БД, хеширования или другая внутренняя ошибка                  |

```bash
curl -i http://localhost:8080/api/v1/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"name":"Анна","email":"anna@example.com","password":"ExamplePass123!"}'
```

## POST /api/v1/auth/login

Авторизация не нужна.

```json
{
  "email": "anna@example.com",
  "password": "ExamplePass123!"
}
```

Оба поля — обязательные строки. Email обрезается по краям и приводится к lowercase. Пароль не преобразуется. Повторной
проверки формата email и длины пароля регистрации нет.

**Успех:** `200 OK`:

```json
{
  "access_token": "<JWT>",
  "token_type": "Bearer"
}
```

Токен действует 2 часа. Полей `expires_in`, `refresh_token` и пользователя в ответе нет. Профиль получайте отдельно
через `/auth/me`.

| HTTP | Текст ошибки                      | Причина                              |
|------|-----------------------------------|--------------------------------------|
| 400  | `Email and password are required` | Пустые credentials после разбора     |
| 401  | `Invalid email or password`       | Нет пользователя или неверный пароль |
| 500  | `Internal server error`           | Внутренняя ошибка сервиса            |

**Оговорка о текущем коде:** если в `Login()` ошибка поиска в БД объединена с отсутствием пользователя, она также
приведёт к `401`. Если применена обновлённая реализация с возвратом ошибки БД, ожидается `500`. Сверьте с актуальным
`handler.go`.

```bash
curl -i http://localhost:8080/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"anna@example.com","password":"ExamplePass123!"}'
```

## GET /api/v1/auth/me

Тело не требуется. Нужен заголовок:

```http
Authorization: Bearer <access_token>
Accept: application/json
```

Схема `Bearer` допускает любой регистр, заголовок должен состоять из двух элементов. Cookie и query token не
используются.

**Успех:** `200 OK`, объект `UserResponse`. Профиль читается из БД на момент запроса.

| HTTP | Текст ошибки               | Причина                                   |
|------|----------------------------|-------------------------------------------|
| 401  | `Bearer token is required` | Нет заголовка или неверный формат         |
| 401  | `Invalid or expired token` | JWT не прошёл проверку                    |
| 401  | `User not found`           | JWT принят, пользователь отсутствует в БД |
| 500  | `Internal server error`    | Ошибка БД или сервиса                     |

```bash
curl -i http://localhost:8080/api/v1/auth/me \
  -H "Authorization: Bearer $ACCESS_TOKEN"
```

`ACCESS_TOKEN` — токен, полученный из `/auth/login`, **не** `JWT_SECRET`.

## Авторизация и роли (JWT middleware)

Для защищённых маршрутов передавайте `Authorization: Bearer <access_token>`.

| JWT claim | Значение                        |
|-----------|---------------------------------|
| `sub`     | UUID пользователя               |
| `role`    | `CLIENT` или `BANK_EMPLOYEE`    |
| `iss`     | `alphahub-api`                  |
| `iat`     | Время выпуска, Unix timestamp   |
| `exp`     | Время истечения, Unix timestamp |

`RequireAuth` проверяет JWT и помещает ID/роль в контекст запроса. `RequireRole` проверяет разрешённую роль. Роль в JWT
отражает момент выдачи токена: её изменение в PostgreSQL не обновляет уже выданный токен. Проверка роли **не заменяет**
проверку принадлежности заявки или компании.

| HTTP | Текст ошибки               | Причина                                        |
|------|----------------------------|------------------------------------------------|
| 401  | `Bearer token is required` | Нет Bearer-заголовка                           |
| 401  | `Invalid or expired token` | Невалидный JWT                                 |
| 401  | `Invalid user ID`          | Нет корректного `sub`                          |
| 401  | `Invalid user role`        | Недопустимый `role`                            |
| 401  | `Unauthorized`             | Нет пользователя в контексте при проверке роли |
| 403  | `Access denied`            | Роль не подходит                               |

Ошибки middleware возвращаются как `text/plain; charset=utf-8`.

## ProductResponse

| Поле                   | Тип             | Значение                                  |
|------------------------|-----------------|-------------------------------------------|
| `code`                 | string          | Уникальный код продукта, первичный ключ   |
| `name`                 | string          | Название                                  |
| `description`          | string          | Описание                                  |
| `min_amount_kopecks`   | integer (int64) | Минимальная сумма в копейках              |
| `max_amount_kopecks`   | integer (int64) | Максимальная сумма в копейках             |
| `min_term_months`      | integer         | Минимальный срок в месяцах                |
| `max_term_months`      | integer         | Максимальный срок в месяцах               |
| `base_annual_rate_bps` | integer         | Базовая годовая ставка в базисных пунктах |
| `is_active`            | boolean         | Доступность для оформления                |

Все поля возвращаются всегда.

```json
{
  "code": "WORKING_CAPITAL",
  "name": "Оборотный кредит",
  "description": "Кредит на пополнение оборотных средств бизнеса",
  "min_amount_kopecks": 30000000,
  "max_amount_kopecks": 500000000,
  "min_term_months": 6,
  "max_term_months": 36,
  "base_annual_rate_bps": 1990,
  "is_active": true
}
```

- `30000000` копеек = 300 000 ₽.
- `500000000` копеек = 5 000 000 ₽.
- `1990` bps = 19,9% годовых.
- Для отображения в JS: `amountRub = amountKopecks / 100`, `ratePercent = baseAnnualRateBps / 100`.
- Базовая ставка не является персональным кредитным предложением.

## GET /api/v1/products

**Авторизация:** не требуется. **Тело:** отсутствует. **Query-параметры:** не используются.

**Успех:** `200 OK`, массив `ProductResponse[]` без обёртки.

```json
[
  {
    "code": "WORKING_CAPITAL",
    "name": "Оборотный кредит",
    "description": "Кредит на пополнение оборотных средств бизнеса",
    "min_amount_kopecks": 30000000,
    "max_amount_kopecks": 500000000,
    "min_term_months": 6,
    "max_term_months": 36,
    "base_annual_rate_bps": 1990,
    "is_active": true
  }
]
```

По текущей реализации:

- Возвращаются только продукты с `is_active = true`.
- Сортировка по `name` по возрастанию.
- Если таких продуктов нет, возвращается `[]`.
- Пагинация отсутствует.

| HTTP | Текст ошибки            | Причина                     |
|------|-------------------------|-----------------------------|
| 500  | `Internal server error` | Ошибка чтения из PostgreSQL |

```bash
curl -i http://localhost:8080/api/v1/products
```

## GET /api/v1/products/{code}

**Авторизация:** не требуется. **Тело:** отсутствует.

Path-параметр `code` — строковый код кредитного продукта, например `WORKING_CAPITAL`.

**Успех:** `200 OK`, один объект `ProductResponse`, как в примере выше.

| HTTP | Текст ошибки            | Причина                             |
|------|-------------------------|-------------------------------------|
| 400  | `Invalid product code`  | Код пустой после удаления пробелов  |
| 404  | `Product not found`     | Продукт не существует или неактивен |
| 500  | `Internal server error` | Ошибка PostgreSQL                   |

Код чувствителен к регистру (`WORKING_CAPITAL` и `working_capital` различаются). Неактивные продукты в этом эндпоинте
скрыты за `404`.

```bash
curl -i http://localhost:8080/api/v1/products/WORKING_CAPITAL
curl -i http://localhost:8080/api/v1/products/UNKNOWN
```

## Текущие ограничения и решения для фронтенда

- В текущем `product.GetAll()` фильтр `is_active = TRUE` скрывает неактивные продукты. Если на экране требуется карточка
  инвестиционного кредита с меткой «Скоро будет доступно», нужно согласовать изменение контракта: например, возвращать
  все продукты и использовать `is_active` для состояния кнопки.
- Публичных API для создания, изменения и удаления продуктов пока нет.
- Предварительный расчёт ежемесячного платежа в `Product API` пока не реализован.
- Для защищённых эндпоинтов используйте Bearer JWT; данные о пользователе можно запросить через `/auth/me`.
- Временные `/client/test` и `/bank/test` не являются бизнес-функциями и могут отсутствовать в финальной сборке.
- Описания `product` отражают подготовленную реализацию Go, но должны быть подтверждены локальными интеграционными
  тестами.

## Проверки для фронтенда

| Сценарий                            | Ожидаемый HTTP |
|-------------------------------------|----------------|
| Регистрация нового клиента          | 201            |
| Повторная регистрация email         | 409            |
| Успешный вход                       | 200            |
| Вход с неверным паролем             | 401            |
| `/auth/me` с валидным JWT           | 200            |
| `/auth/me` без JWT                  | 401            |
| Список активных продуктов           | 200            |
| Активный продукт по коду            | 200            |
| Несуществующий / неактивный продукт | 404            |
| Неверный HTTP-метод                 | 405            |
