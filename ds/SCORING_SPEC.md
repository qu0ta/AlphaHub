# Спецификация финансового скоринга

Версия правил: `financial_rules_v1`.

Score находится в диапазоне 0–100.
Чем выше балл, тем лучше финансовая оценка компании.

Score не является вероятностью возврата кредита.
Веса и пороги — демонстрационные правила MVP, без калибровки
на реальных данных о погашении кредитов.

## Вход и выход

Вход: `ScoringInput`.

Обязательные данные:
- ИНН;
- сумма кредита в копейках;
- срок в месяцах;
- годовая ставка `annual_rate_bps`: 1990 = 19,90%;
- дата первоначальной подачи `application_date`;
- финансовые показатели за шесть полных месяцев перед датой подачи;
- заявленный ежемесячный платёж по действующим кредитам.

Месяцы передаются в хронологическом порядке.
При повторном расчёте сохраняется первоначальная дата подачи.

Ставку и дату передаёт бэкенд, они не извлекаются из PDF.

Выход: `ScoringResponse`:
- `score`;
- `explanation.positive_factors`;
- `explanation.negative_factors`;
- `model_version`.

## Финансовые показатели

Для каждого месяца:

CF = операционные поступления - операционные выплаты - налоги.

Операционные выплаты не включают налоги и кредитные платежи.
Средний денежный поток — сумма CF за шесть месяцев / 6.

Средняя выручка — сумма выручки за шесть месяцев / 6.

Коэффициент вариации:

CV = sqrt(sum((выручка месяца - средняя выручка)^2) / 6)
     / средняя выручка.

Динамика:

G = средняя выручка последних трёх месяцев
    / средняя выручка первых трёх месяцев - 1.

Платёж по новому кредиту:

r = annual_rate_bps / 120000
P = сумма кредита * r / (1 - (1 + r)^(-срок))

При нулевой ставке:
P = сумма кредита / срок.

Используется аннуитет без комиссий и льготных периодов.
Платёж округляется до целой копейки через ROUND_HALF_UP.
Промежуточные средние не округляются до целых копеек.
Вычисления выполняются через Decimal.

Покрытие платежей:

C = средний денежный поток
    / (заявленный действующий платёж + новый платёж).

## Начисление баллов

### Покрытие платежей — до 60 баллов

| C | Баллы |
|---|---:|
| C < 1 | 0 |
| 1 ≤ C < 1.2 | 15 |
| 1.2 ≤ C < 1.5 | 30 |
| 1.5 ≤ C < 2 | 45 |
| C ≥ 2 | 60 |

### Стабильность выручки — до 20 баллов

| CV | Баллы |
|---|---:|
| 0 ≤ CV ≤ 0.10 | 20 |
| 0.10 < CV ≤ 0.25 | 15 |
| 0.25 < CV ≤ 0.50 | 5 |
| CV > 0.50 | 0 |
| Не определён из-за нулевой выручки | 0 |

### Динамика выручки — до 20 баллов

| G | Баллы |
|---|---:|
| G < -0.20 | 0 |
| -0.20 ≤ G < -0.05 | 5 |
| -0.05 ≤ G < 0.05 | 10 |
| G ≥ 0.05 | 20 |
| Не определена из-за нулевой базы | 0 |

## Итоговый score

raw_score = баллы покрытия + баллы стабильности + баллы динамики.

Если C < 1:
score = min(raw_score, 39).

Иначе:
score = raw_score.

Отрицательный и нулевой денежный поток при положительных платежах
дают C < 1 и обрабатываются по этому правилу.

## Отсутствующие данные и нулевые знаменатели

- Пропущенные обязательные поля, null и недопустимые значения
  отклоняются схемой. Успешный ScoringResponse не формируется.
- Отсутствующие значения нельзя заменять нулями.
- При нулевой средней выручке CV = None, баллы стабильности = 0.
- При нулевой средней выручке первых трёх месяцев G = None,
  баллы динамики = 0.
- При нулевой сумме платежей C = None.
  calculate_score() вызывает ValueError.
- Ошибка расчёта не является score = 0 и не означает отказ.

Отсутствие данных и коэффициент, не определённый из-за нулевых
значений, — разные ситуации.

## Объяснения

Положительные и отрицательные факторы формируются из правил,
которые сработали при расчёте.

Нейтральная динамика (-5% ≤ G < 5%) даёт 10 баллов без отдельного
фактора. Поэтому отсутствие отрицательных факторов не означает
максимальный score.

## Пороги для модуля решений

Предлагаемые пороги MVP, подлежащие согласованию с бэкендом:

| Score | Базовое действие |
|---|---|
| 0–39 | Отказ по финансовой оценке |
| 40–69 | Ручное рассмотрение |
| 70–100 | Кандидат на автоматическое одобрение |

Модуль скоринга возвращает балл и объяснения.
Окончательное решение принимает отдельный модуль.

Перед применением порогов проверяются полнота и пригодность данных.
Итоговое решение учитывает стоп-факторы, лимиты продукта и результаты
внешних проверок. Противоречия могут потребовать ручного рассмотрения
при любом score. Технический сбой не является основанием для отказа.

## Ручные примеры

| C | CV | G | Расчёт | Score |
|---|---|---|---|---:|
| 2.0 | 0 | 0 | 60 + 20 + 10 | 90 |
| 1.3 | 0.20 | 0 | 30 + 15 + 10 | 55 |
| 0.9 | 0.08 | 0.10 | min(0 + 20 + 20, 39) | 39 |
| 2.0 | 0.20 | -0.25 | 60 + 15 + 0 | 75 |

## Ограничения

- Оцениваются только финансовые показатели.
- Возраст бизнеса и кредитная история не входят в текущий score.
- Шесть месяцев не позволяют надёжно оценить сезонность.
- При хорошем покрытии сильное падение выручки может сочетаться
  с высоким score. Это свойство текущих правил, которое команда
  должна принять либо изменить до утверждения спецификации.

## Проверка

Из папки ds:

```bash
python -m unittest -v test_metrics test_scoring test_schema_contract
```

Ожидается 22 успешных теста.
Тесты проверяют расчёты, границы правил и входной контракт.
Они не подтверждают точность прогнозирования реальных дефолтов.

## Аналитический эксперимент: правила и модель

В ds/experiments реализовано независимое исследование по ТЗ: синтетические
заявки stable/medium/risky, случайные метки дефолта, шум и стресс, три seed,
разбиение 70/15/15 и Logistic Regression. С текущим порогом score >= 70
сравниваются ошибки I/II рода и их условная стоимость (LGD 45%, доходность 8%).
Исходное трёхуровневое распределение решений правил сохраняется отдельно.
Исследование не изменяет формулы, рабочий API или решения MVP.

Запуск из ds: python -m experiments.run_experiment.
Методика и параметры: [experiments/README.md](experiments/README.md).
