# Исследование кредитного скоринга AlphaHub

Независимый модуль по ТЗ «Rule-based vs Machine Learning». Сравнивает существующий
`scoring.py` и Logistic Regression по классификации дефолтов, стоимости ошибок
и устойчивости к шуму и стрессу. PDF-парсер, REST API, формулы и решения MVP
не используют обученную модель и продолжают работать как прежде.

**Все данные и метки синтетические. Результат не доказывает превосходство
какого-либо метода на реальных банковских клиентах.**

## Запуск

Требуется Python 3.12. Из корня проекта создать отдельное окружение:

```bash
python3 -m venv .venv-scoring
.venv-scoring/bin/python -m pip install -r ds/experiments/requirements.txt
```

Из каталога `ds` с активированным окружением выполнить одну команду:

```bash
python -m experiments.run_experiment
```

Без активации окружения из `ds`:

```bash
../.venv-scoring/bin/python -m experiments.run_experiment
```

По умолчанию: 6000 заявок на набор, seed 42/43/44 и сценарии base/high_noise/stress,
всего 54 000 уникальных заявок. Base делится на 4200/900/900; обучение — только
на train, выбор порога — только на validation. Та же модель и замороженный порог
проверяются на base test и отдельных наборах high_noise и stress по 6000 заявок.

Результат: `data/`, `models/`, `results/` внутри `experiments`. Для отдельного запуска:

```bash
python -m experiments.run_experiment --output /tmp/alphahub-scoring-study
python -m experiments.run_experiment --config experiments/config.example.json
```

## Конфигурация генератора

В JSON можно изменить `samples` (минимум 5000), `seeds` (минимум три разных),
`economics` и отдельные поля сценариев. Неуказанные поля сохраняют значения
из `config.py`. Фактическая конфигурация записывается в `results/metrics.json`.

| Поле сценария | Значение |
|---|---|
| `observation_noise` | Стандартное отклонение логарифма шума наблюдений; средний множитель 1 |
| `volatility_multiplier` | Множитель месячных колебаний внутри профиля |
| `seasonal_amplitude` | Амплитуда сезонности с индивидуальной фазой |
| `shock_probability`, `shock_scale` | Частота и величина разовых положительных/отрицательных шоков |
| `inflow_multiplier` | Множитель операционных поступлений |
| `expense_multiplier` | Множитель отношения операционных расходов к поступлениям |
| `risk_shift` | Сдвиг скрытого логита дефолта |
| `hidden_risk_std` | Разброс ненаблюдаемого фактора риска |

Профили stable/medium/risky задают перекрывающиеся диапазоны тренда, расходов,
волатильности и действующего платежа. Они используются генератором и при анализе
распределений, но не передаются модели. Метка `default` семплируется по отдельной
вероятностной модели латентных финансов: покрытие платежей, денежная маржа,
CV, динамика, долг, срок, нелинейное взаимодействие низкой маржи и высокого долга,
скрытый будущий шок и случайный фактор. Score правил при генерации таргета
не используется. Истинная PD и скрытые факторы в датасет не экспортируются.

Горизонт исхода фиксирован: 12 месяцев. Целевой диапазон дефолтов base — 10–25%.
Фактические доли проверяются и сохраняются без пересэмплирования под победу алгоритма.

## Признаки и обучение

Разбиение уникальных клиентов: `train_test_split` с `stratify` и фиксированным
`random_state`, 70/15/15. Генератор создаёт одного клиента на заявку. При повторных
клиентах функция разделения использует 20 групповых стратифицированных folds,
объединённых 14/3/3; пропорции приблизительные, клиент остаётся в одной выборке.
Для группового режима нужны минимум 20 клиентов и 20 наблюдений каждого класса.

Признаки рассчитываются только из `ScoringInput` через `metrics.py`: средняя
выручка, средний денежный поток, CV, рост, действующий платёж и его отношение
к выручке, покрытие действующего платежа, новый платёж, покрытие всех платежей,
сумма кредита к месячной выручке, срок, ставка.

Pipeline: `SimpleImputer(median)` → `StandardScaler` →
`LogisticRegression(C=1, max_iter=2000)`. Все стадии обучаются только на train.
Неопределённые производные коэффициенты заполняются медианами train; обязательные
исходные финансы валидируются существующим `ScoringInput`.

Порог PD минимизирует стоимость ошибок на validation; равенство PD порогу означает
отказ. При равной стоимости предпочитается меньше одобрений. На test/high_noise/stress
не переобучается ни модель, ни преобразования, ни порог. HistGradientBoosting
не включён: дополнительная модель в ТЗ необязательна.

## Сравнение и финансы

Положительный класс — дефолт. Прогноз 1 означает отказ, прогноз 0 — одобрение.
Правила вызываются через реальный `scoring.score_application`: score ≥ 70 —
одобрение. Исходные REJECT (0–39), MANUAL (40–69), AUTO_APPROVE (70–100)
сохраняются отдельно. В бинарном сравнении MANUAL входит в «нет автоматического
одобрения», но в MVP это ручная проверка, а не автоматический отказ.

FP — отказ недефолтному клиенту, FN — одобрение дефолтного. Для обоих методов:
Accuracy, Precision, Recall, F1, ROC-AUC, PR-AUC (average precision), матрица ошибок,
FPR и FNR. Для ML также Brier и калибровка; rule score не трактуется как PD.

```text
Чистая прибыль успешного кредита = 8% суммы
LGD                              = 45% суммы
Cost      = Σ(FN_amount × LGD) + Σ(FP_amount × net_yield)
ML effect = Cost правил − Cost ML
Снижение потерь (%) = ML effect / Cost правил × 100
```

Деньги — целые копейки; каждая суммарная компонента округляется `ROUND_HALF_UP`.
Положительный эффект означает меньшую условную стоимость ошибок ML.
При нулевой базе относительный эффект не определён. Доходность 8% относится
ко всему сценарию и не является годовой ставкой или маржой реального продукта.
Цена ручной проверки задана как 1000 ₽, но в бинарном эксперименте применяется 0 ₽.
Чувствительность: LGD=25/45/65%, доходность=4/8/12%, прогнозы и пороги фиксированы.

## Файлы результата

| Файл | Содержимое |
|---|---|
| `data/synthetic_clients.csv` | Полный base первого seed: снимок ScoringInput, default, профиль и признаки |
| `data/seed_<seed>_<scenario>.csv` | Другие наборы всех seed/сценариев |
| `models/logistic_regression.joblib` | Pipeline первого seed, порог, признаки, конфигурация и источник обучения |
| `models/logistic_regression_seed_<seed>.joblib` | Другие модели |
| `results/metrics.json` | Метрики, три уровня правил, распределения, чувствительность, mean/SD, конфигурация и SHA-256 данных |
| `results/predictions.csv` | Все оценённые заявки: seed, сценарий, default, score, исходное решение, PD и бинарные прогнозы |
| `results/financial_comparison.csv` | Суммы FP/FN, потери и эффект |
| `results/splits.csv` | Принадлежность заявок к train/validation/test |
| `results/report.md` | Итоговый отчёт по ТЗ со ссылками на графики |

Финансовая история хранится в `scoring_input_json`; восстановление:
`ScoringInput.model_validate_json(record["scoring_input_json"])`.
CSV содержит метки и профили для анализа, но обучение использует только явный
список `FEATURE_NAMES` из `features.py`. Joblib предназначен для локального
исследования: загружать следует собственные артефакты в том же окружении.

Строятся 8 графиков в PNG и SVG: распределения клиентов, ROC, матрицы ошибок,
FP/FN, финансовые потери, стоимость по порогу, устойчивость по сценариям, калибровка.
Графики base относятся к первому seed, график устойчивости — ко всем seed.

Размеры оценки различаются: base test — 15%, дополнительные наборы — 100%.
Поэтому между сценариями сравниваются также потери на одну заявку. По seed
рассчитываются средние и выборочные SD (ddof=1), без выбора удачного запуска.
Это разброс моделируемых условий, а не доверительный интервал для реального банка.

Данные, модели и результаты исключены из Git и воспроизводятся одной командой.
[Зафиксированные итоги](../../docs/ds/SCORING_BENCHMARK_RESULTS.md).

## Проверки

Из `ds`:

```bash
../.venv-scoring/bin/python -m unittest experiments.test_experiments test_metrics test_scoring test_schema_contract -v
```

Тесты проверяют генерацию, стохастичность, отсутствие утечки, стратификацию,
изоляцию клиентов, соответствие scoring.py, стоимость FP/FN, подбор порога,
обучение преобразований только на train и сохранение неизменной модели.
