# Миграции кредитного процесса AlphaHub

Формат: golang-migrate/migrate v4, PostgreSQL. 13 версий, 26 SQL-файлов.
SQL рассчитан на PostgreSQL 16 из compose.yaml. Каждая миграция обёрнута в BEGIN/COMMIT.
Применение миграций из Go-кода и установка CLI этим набором файлов не добавляются.

## Порядок

| Версия | Изменение |
| --- | --- |
| 1 | users: исходная схема, совместимая с текущим auth |
| 2 | companies и FK users.company_id |
| 3 | products |
| 4 | applications; accepted_offer_id пока без FK |
| 5 | documents |
| 6 | financial_records |
| 7 | check_results |
| 8 | scoring_results |
| 9 | decisions |
| 10 | offers |
| 11 | FK принятого предложения и проверка принадлежности заявке |
| 12 | info_requests |
| 13 | status_history |

Обратный порядок down снимает зависимости до удаления таблиц; DROP CASCADE не используется.
Старый 001_create_users.sql заменён парой 000001_create_users.up/down.sql.
Первая up-миграция сохраняет исходные столбцы, ограничения и индекс users без ужесточения.
Последующие версии добавляют ограничения по мере появления связанных сущностей.

## Запуск через Docker Compose

Из корня AlphaHub:

~~~powershell
docker compose run --rm migrate
docker compose run --rm migrate version
~~~

Сервис ждёт готовности postgres и по умолчанию выполняет up.
Используется внутренний адрес postgres:5432; DATABASE_URL в PowerShell для этого сервиса не нужна.
SQL-файлы подключены к /migrations только для чтения.
Профиль tools исключает одноразовый сервис из обычного docker compose up; явный run migrate работает без --profile.
Первый запуск скачивает образ migrate/migrate:v4.20.1.

Если users уже создана вручную, сначала выполните проверки исходной схемы из раздела ниже.
Только после подтверждения соответствия версии 1 её можно зарегистрировать отдельно:

~~~powershell
docker compose run --rm migrate force 1
docker compose run --rm migrate
~~~

force не включён в автоматический запуск. Если версия уже ведётся, её нельзя без проверки менять на 1.
При необходимости отката одной версии: docker compose run --rm migrate down 1 — это может удалить данные.

## Запуск на новой базе

Нужны установленный CLI migrate v4 с драйвером postgres и готовая PostgreSQL.
Из каталога backend, PowerShell, при уже заданной переменной DATABASE_URL:

~~~powershell
migrate -path ./migrations -database $env:DATABASE_URL version
migrate -path ./migrations -database $env:DATABASE_URL up
migrate -path ./migrations -database $env:DATABASE_URL version
~~~

На новой базе первая команда version может сообщить, что миграции ещё не применены.
Последняя должна показать версию 13 без dirty.
Наличие backend/.env само по себе не задаёт $env:DATABASE_URL для CLI: переменную нужно
задать в текущем процессе или передать DSN иным способом. Секреты не коммитить.
Миграции не создают БД и не загружают демонстрационные продукты/пользователей.
UUID генерируются приложением, как уже делает auth; расширение uuid-ossp не требуется.

## Если users уже создана старым SQL вручную

Не запускайте первую миграцию поверх существующей users: CREATE TABLE завершится ошибкой.
Не удаляйте таблицу с нужными данными. Сначала сделайте резервную копию.

1. Проверьте, что именно users создана исходным 001_create_users.sql, а остальных таблиц
   из этого набора ещё нет. Если схема уже другая, нужен отдельный план перехода.
2. Сравните колонки/типы/nullability/default и определения ограничений с версией 1:

~~~sql
SELECT column_name, data_type, character_maximum_length, is_nullable, column_default
FROM information_schema.columns
WHERE table_schema = 'public' AND table_name = 'users'
ORDER BY ordinal_position;

SELECT conname, pg_get_constraintdef(oid)
FROM pg_constraint WHERE conrelid = 'public.users'::regclass;

SELECT indexname, indexdef FROM pg_indexes
WHERE schemaname = 'public' AND tablename = 'users';

SELECT id, company_id FROM users WHERE company_id IS NOT NULL;
~~~

Последний запрос важен: после версии 2 непустые company_id должны ссылаться на companies.
Если ссылки уже заполнены, сначала подготовьте соответствующие реальные компании в рамках
согласованного перехода; миграция не выдумывает их и не обнуляет ссылки пользователей.

3. Проверьте существующий учёт migrate. Если он уже ведётся, не перезаписывайте версию вслепую.
4. Только после подтверждения соответствия users версии 1 зарегистрируйте исходную версию:

~~~powershell
migrate -path ./migrations -database $env:DATABASE_URL force 1
migrate -path ./migrations -database $env:DATABASE_URL up
~~~

force 1 НЕ выполняет SQL: это регистрация проверенного исходного состояния, не исправление схемы.
Если обычный up уже упал и оставил dirty, сначала проверьте фактическую схему и причину сбоя.
Не используйте force для пропуска неизвестной ошибки.

## Откат

~~~powershell
migrate -path ./migrations -database $env:DATABASE_URL down 1
~~~

Откаты удаляют соответствующие таблицы вместе с данными и не являются резервной копией.
Повторный up восстанавливает структуру, но не удалённые записи.
При откате компаний остающийся users.company_id больше не защищён FK; последующий up
потребует восстановить компании для сохранённых ссылок.
На production предпочтителен проверенный план изменения и исправляющая up-миграция.
Опубликованные и применённые версии не редактировать: добавлять следующую.

## Принятые соглашения

- Имена таблиц во множественном числе, кроме status_history, согласованы с существующей users.
- company_id — UUID: совпадает с PK companies и текущим auth. На картинке USER.company_id
  обозначен varchar; эта неоднозначность устранена в пользу UUID.
- Время — TIMESTAMPTZ вместо timestamp без часового пояса на схеме.
- Деньги — BIGINT в копейках; ставки — INTEGER в базисных пунктах: 1500 = 15% годовых.
- Суммы кредита и сроки положительные; расходы, выручка, долговые платежи и ставки неотрицательные.
- ИНН — 10 или 12 цифр без проверки контрольной суммы; ОКВЭД и business_type — непустые строки.
- period_month — первое число месяца. Одна запись на заявку/версию/месяц.
- data_version и offer.version положительные; версия предложения уникальна внутри decision.
- Статусы, типы решений/проверок и risk_band не ограничены выдуманными ENUM:
  картинка не задаёт справочники. Для обязательных статусов проверяется непустая строка.
  У новой заявки DEFAULT status='DRAFT', data_version=1.
- Диапазон score не задан схемой, поэтому ограничения вроде 0..1000 не навязаны.
- Структура JSONB не зафиксирована: схема не определяет форму required_items/features.
- Nullable-поля соответствуют знакам вопроса на схеме; users.company_id также nullable,
  чтобы текущая регистрация без компании продолжала работать.
- FK используют стандартный NO ACTION: удаление родителя не стирает финансовую историю.
  Индексы покрывают внешние ключи и основные выборки по заявке/версии/статусу.

Эти соглашения следует учитывать при реализации сервисов. При изменении бизнес-требований
после применения набора создавайте дополнительные миграции.

## Межтабличная целостность и обязанности сервиса

База проверяет, что исходный документ финансовой записи принадлежит той же заявке,
а скоринг решения — той же заявке и data_version.
Принятое предложение принадлежит той же заявке через offers -> decisions;
это обеспечивают constraint triggers на applications, offers и decisions.
Один offer нельзя связать как принятый с несколькими заявками.
Триггеры DEFERRABLE INITIALLY IMMEDIATE: обычно проверяют каждую команду;
при явно отложенных ограничениях проверяется конечное состояние транзакции.

Сервис должен проверять владельца/роль, допустимые переходы статусов, диапазоны продукта,
срок действия предложения при принятии, актуальность data_version и права подписанта.
Также сервис управляет updated_at, data_version и добавлением status_history.
DEFAULT now() устанавливает время создания, но не обновляет updated_at при UPDATE.
Запись статуса и истории выполняйте одной бизнес-транзакцией.
Таблицы сами по себе не реализуют проверки, скоринг, хранение файлов или HTTP API.

## Проверка набора

SQL проверен на изолированном PostgreSQL через PGlite:
создание 12 таблиц, вставка связанного кредитного процесса, полный down с данными,
повторный up и отдельные up/down/up на пустой схеме.
Проверены 15 отклоняемых операций: FK, уникальность, суммы, месяц, совпадение версии
скоринга, принадлежность документа и принятого предложения, включая изменение их родителей.
Проверен переход с прежней users и сохранение существующего пользователя.
Это проверка SQL, не отчёт о запуске migrate CLI или PostgreSQL 16 в Docker.
Рабочая БД не изменялась.


## Формат объяснения скоринга

В scoring_results.explanation обязательно передаётся JSON-объект с двумя массивами:

~~~json
{
  "positive_factors": ["Стабильная выручка"],
  "negative_factors": ["Высокая долговая нагрузка"]
}
~~~

Оба ключа обязательны, пустые массивы допустимы. null, строка, объект вместо массива
и отсутствие любого из ключей отклоняются CHECK-ограничением.
Формат элементов массивов не ограничен: это могут быть строки или объекты с деталями.
Дополнительные ключи верхнего уровня разрешены.
Поле остаётся JSONB NOT NULL без значения по умолчанию.
Изменена исходная миграция №8: уже применённая версия автоматически повторно не выполняется.
